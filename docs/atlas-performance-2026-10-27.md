# 地图资源与拖动验证 · 2026-10-27

## 改动

- 只挂载视口和 240 屏幕像素缓冲区内的论文卡片，额外保留当前选中卡片。所有论文仍可通过索引、搜索、分支和全览定位。
- 地形、路线、论文层和小地图静态部分拆为 memo 组件。路线几何在内容初始化时计算，不随每次相机移动重新计算。
- pointer / wheel 的相机更新由 `requestAnimationFrame` 合并；清理时取消未完成帧。固定背景网格，拖动时关闭卡片过渡。
- 常规缩放使用最大 640 × 400 的 WebP 预览，异步解码、延迟加载；画布缩放超过 110% 或打开阅读面板时使用原图。
- 圈层容量从固定三圈改为随分支增长的 2、3、4、5…个节点，岛屿尺寸与相互位置一起计算。测试覆盖单分支 20 篇，防止扩容时丢节点或重叠。

没有新增运行时依赖。预览生成需要 Python / Pillow / PyMuPDF，生成结果已纳入仓库，网站运行与部署无需 Python。

## 资源体积

以下是文件字节合计，不是某次页面请求的网络传输量。实际加载受可见范围、懒加载和浏览器缓存影响。

| 范围 | 高清原图 | 画布预览 |
| --- | ---: | ---: |
| 原有 43 项 | 5,584,522 B | 869,754 B |
| 扩充后 76 项 | 8,568,022 B | 1,626,476 B |

76 项预览总量比其原图减少约 81%。在全览中全部卡片可见，会挂载所有卡片，但仍使用预览；没有通过删除论文或减小原图来换取速度。

## 拖动样本

Windows，Node 24.14.1，Next.js 开发模式，Codex IAB，1280 × 720；等待初始定位后，在 62% 缩放、关闭侧栏的页面上从 (340, 420) 拖到 (570, 440)。临时在 `AtlasCanvas` 外添加 React `Profiler`，记录 update 阶段的 `actualDuration`，每次样本均包含 9 次更新。测试后已移除 Profiler。

| 版本 | 论文量 | 中位更新耗时 | 最大更新耗时 | 更新耗时合计 |
| --- | ---: | ---: | ---: | ---: |
| 修改前，基于 de79f84 | 43 | 25.1 ms | 34.9 ms | 195.7 ms |
| 渲染优化后，同样内容 | 43 | 3.0 ms | 7.3 ms | 31.8 ms |
| 渲染优化且扩充内容后 | 76 | 2.3 ms | 6.4 ms | 28.5 ms |

优化后的 43 项样本拖动结束挂载 8 张卡片，76 项样本结束挂载 9 张。原版始终挂载全部 43 张。原始数据见 [样本 JSON](atlas-performance-samples.json)。

这是单次开发环境诊断，反映 React 更新工作量，**不是 FPS、浏览器绘制耗时、GPU 性能或生产性能保证**。76 项样本与 43 项的初始论文位置也随布局增长而改变，不能把 2.3 ms 与 3.0 ms 的小差异解释为论文越多越快。

## 功能与边界

自动验证目录、来源、图示、预览体积、相邻阅读连线、卡片不重叠、扩容容量、视口边缘与缓冲区、缩放锚点、桌面和手机全览。人工检查 76 项首屏、同路径拖动、11 篇分支、搜索 RVT 并定位 RVT-2、高清阅读侧栏、375 × 812 手机全览。手机全览无页面横向溢出，76 张卡片均可进入视野；全览只用于定位，阅读时应进入分支或单篇。
